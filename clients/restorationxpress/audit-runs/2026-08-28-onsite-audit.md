## Recommended next actions (priority order)

1. **(money page, accessibility)** On `/contact/`, underline the `mailto:issac@restorationxpress.com` link in the body copy. It is currently distinguished from surrounding text by colour alone at 1.59:1 contrast, which fails WCAG. Adding `text-decoration: underline` to in-prose links fixes it site-wide and is a one-line CSS change.
2. **(template, high impact)** Replace `/images/logo.png` with a 298x128 WebP. The current file is a 1000x429 PNG at 158,570 bytes rendered into a 149x64 box, on all 6 audited pages and presumably all 90 site pages. Estimated saving is about 157KB per page load, the single largest byte win available.
3. **(template, accessibility)** Darken the brand primary from `#719430` to approximately `#5A7726` wherever it is used as text on white or as a background behind white text. At 3.51:1 the current value fails AA for the header CTA, the "Call Now" buttons, the top notice bar, and the footer phone link. The accent `#93b652` behind white text is 2.31:1 and should not be used for text at all.
4. **(template, schema)** Add the missing `item` property to the final `ListItem` in the `BreadcrumbList` JSON-LD. Every page except the homepage emits a last crumb with `position` and `name` only. This is the only medium-severity on-page issue on the site and clearing it moves five pages from amber to green.
5. **(template, performance)** Add `fetchpriority="high"` to the hero `<img>` on the services hub, service-landing, service-area, and contact layouts. The homepage already sets it correctly. Low absolute gain on desktop, but it is the one lever that will matter most once mobile auditing is available.

## Notes / caveats

- **Desktop only.** The Lighthouse run used `formFactor=desktop`, `cpuSlowdownMultiplier=1`, `throughputKbps=10240`. Mobile scores typically run 10-20 performance points lower and were not measured. Do not represent these numbers as mobile-first. Note that calling the DataForSEO API directly (rather than through the MCP wrapper) does expose a `for_mobile` flag, so a mobile pass is achievable in a future run if the methodology is updated to ask for it.
- **Client record status.** `clients/restorationxpress.json` still has `status: "onboarding"`. The audit proceeded anyway because `build_status` is `pushed_main` and `apex_cutover.completed_at` is set to 2026-08-04, so the site is genuinely live. The ops owner should flip status to `active`.
- **Fresh deploy.** A main-branch deploy landed at 2026-08-28T01:14:51Z, roughly two minutes before this scan. Scores reflect that build.
- **Phone numbers are fine on the live site.** The site ships a client-side call-tracking swap: server-rendered HTML contains (954) 932-5420, which matches the `schema.org` `telephone` value, and JavaScript rewrites visible `tel:` links to the tracking number (954) 686-1404 after hydration. This is the correct implementation, since crawlers index the NAP-consistent number. No action needed.
- **Stale number in repo plan files only.** `plan-input.json` and `plan/url-plan.json` still carry a third number, (954) 964-6471, which appears nowhere on the live site. This is repo data hygiene, not a site defect, but it will propagate into future generated titles and meta descriptions if left in place.
- **The Google Maps iframe is correctly configured.** DataForSEO flagged `frame` on `/service-areas/fort-lauderdale-fl/`. The embed carries `loading="lazy"`, a descriptive `title`, and `referrerpolicy`. Informational, not a defect.
- **No broken links, no broken resources, no mixed content, no redirect issues** were detected on any of the 6 URLs. Canonicals are present and self-referencing correctly on all pages. Security headers are in good shape (HSTS, CSP frame-ancestors, `X-Content-Type-Options`, Referrer-Policy, Permissions-Policy all present).
